# 自研四大件蓝图专项

## 当前结论

本专项成立，而且应作为中长期主线蓝图存在。

目标不是继续替换第三方 DLL 的文件名，也不是先把 `Well` 膨胀成一个“大锅宿主”，而是把当前依赖的 WRobot 四层能力，收敛成 SpellFire 自己可控的四层组件体系：

1. `MemoryRobot.dll` 对位层
2. `robotManager.dll` 对位层
3. `wManager.dll` 对位层
4. `RDManaged.dll` 对位层

当前真实建议：

1. 方向上重新设计
2. 实现上复用 `Well` 里已经成熟的底层能力
3. 工程上拆成四层，不把所有职责塞进 `Well`

## 为什么不是先改造 Well

`Well` 当前更像：

1. 注入壳
2. 远控/内存调用底座
3. 本项目旧主链的底层实现集合

它不像：

1. WoW 语义层
2. 产品生命周期层
3. 导航网格引擎层
4. 完整运行时组件总线

如果直接把四大件全塞进 `Well`，会出现三个问题：

1. 宿主、内存底座、游戏语义、导航引擎混成一锅
2. 后续 Runtime 与 Navigation 的边界再次塌掉
3. 最终仍然得二次拆分，返工更重

因此 `Well` 不应被改造成“全能四大件总成”，而应被视作：

1. `SpellFire.MemoryRobot` 的底座来源
2. `SpellFire.RuntimeHost` 的可复用宿主经验来源
3. 旧主链历史包袱的逐步抽离对象

## 四大件对位图

### 1. `SpellFire.MemoryRobot`

对应第三方：

1. `MemoryRobot.dll`

职责：

1. 进程打开/关闭
2. 句柄、模块、页面保护、地址读写
3. 远程可执行内存
4. 汇编调用/代码洞/底层 patch 支撑

不负责：

1. WoW 对象语义
2. Lua
3. 产品生命周期
4. 导航寻路

来源建议：

1. 优先复用 `Well` 已稳定的内存读写与远控基础
2. 把真正通用的能力抽走，而不是照搬 `Well` 全仓

### 2. `SpellFire.RuntimeHost`

对应第三方：

1. `robotManager.dll`

职责：

1. Hook runtime context
2. attach/ready 状态
3. alloc text/data
4. 线程挂接
5. 生命周期清理
6. 产品/动作执行前置门禁

不负责：

1. WoW 语义对象模型
2. 路径规划算法
3. 上层导航编排

当前边界提醒：

1. 这一层不是先做 Products 全家桶
2. 先做“最小可附着、最小可 ready、最小可清理”闭环

### 3. `SpellFire.WowRuntime`

对应第三方：

1. `wManager.dll`

职责：

1. `Memory`
2. `ObjectManager`
3. `Usefuls`
4. `MovementManager`
5. `ClickToMove`
6. `Lua`
7. `PathFinder` 的 WoW 语义封装

不负责：

1. 原始注入
2. 低层汇编组装
3. Recast 网格引擎本体

当前与现有 Runtime 的关系：

1. `SpellFire.Runtime` 是主程序共享运行时地基
2. `SpellFire.WowRuntime` 未来应作为 `SpellFire.Runtime` 下面的具体 WoW 语义组件来源
3. 不应让 `SpellFire.Runtime` 自己变成“大而全的 wManager 替身项目”

### 4. `SpellFire.NavMesh`

对应第三方：

1. `RDManaged.dll`

职责：

1. Recast/Detour 网格加载
2. `FindPath`
3. `FindZ`
4. tile 管理

不负责：

1. 对象层
2. Lua
3. Attach/Hook
4. 动作发送

当前判断：

1. 这是四大件里最适合独立专项的一层
2. 它与前三层耦合最弱
3. 不应掺进 WoW 语义或宿主逻辑

## `fasmdll_managed.dll` 的口径

它不应被归为“四大件同级核心”。

更准确的定位是：

1. 底层汇编辅助依赖
2. 可能服务于 `MemoryRobot` / `RuntimeHost` 的实现细节
3. 不是 WoW 语义层核心
4. 不是导航引擎核心

它通常承担的角色：

1. 机器码拼装
2. 汇编生成桥
3. 注入/patch/code cave 的底层配套

因此本专项的口径必须是：

1. `fasmdll_managed.dll` 不是四大件之一
2. 它只是在某些实现路线下，可能成为 `SpellFire.MemoryRobot` 或 `SpellFire.RuntimeHost` 的内部依赖
3. 如果后续改成自管机器码模板或别的汇编方案，它可以被替换，甚至移除

## 推荐施工顺序

不要按“哪个名字最熟就先造哪个”推进。

推荐顺序：

1. `SpellFire.MemoryRobot`
2. `SpellFire.RuntimeHost`
3. `SpellFire.WowRuntime`
4. `SpellFire.NavMesh`

原因：

1. 前两层是后三层的底座
2. `Well` 当前最容易复用的正是前两层素材
3. `wManager` 语义层如果先做，很容易继续偷吃旧底层和第三方 DLL
4. `RDManaged` 最独立，适合最后单开

## 与当前工程的关系

### 当前 `SpellFire.Runtime`

它现在的定位应保持：

1. 主程序共享运行时地基
2. 运行时契约/模型/服务汇聚层
3. 第三方组件消费层

它现在不应直接承担：

1. 四大件源码总仓
2. 内存底座实现全集
3. 宿主壳全集

更合适的关系是：

1. `SpellFire.Runtime` 消费 `SpellFire.MemoryRobot`
2. `SpellFire.Runtime` 消费 `SpellFire.RuntimeHost`
3. `SpellFire.Runtime` 消费 `SpellFire.WowRuntime`
4. `SpellFire.Runtime` 消费 `SpellFire.NavMesh`

### 当前 `Well`

它的后续命运不应是继续膨胀，而应是：

1. 抽底层
2. 留壳
3. 慢慢瘦身

也就是说：

1. 能抽成 `MemoryRobot` 的先抽
2. 能抽成 `RuntimeHost` 的再抽
3. 最后 `Well` 只保留主注入壳、兼容旧链的最低限度职责

## 第一阶段施工目标

本专项第一阶段不要求立刻做出“四大件可运行成品”。

第一阶段只做三件事：

1. 画清项目骨架
2. 识别 `Well` 可抽取底层资产
3. 给出第一刀可落地迁移单

### 第一刀建议

第一刀建议不是碰 `SpellFire.WowRuntime`，而是先开：

1. `SpellFire.MemoryRobot`

范围：

1. 内存打开/关闭
2. 基础读写
3. 模块信息
4. 页面保护/可执行内存
5. 远程调用底座中真正通用的部分

不做：

1. WoW 对象模型
2. Lua
3. 产品层
4. 导航网格

## 拟定项目骨架

建议未来落成以下项目：

1. `SpellFire.MemoryRobot`
2. `SpellFire.RuntimeHost`
3. `SpellFire.WowRuntime`
4. `SpellFire.NavMesh`
5. `SpellFire.Runtime`

关系建议：

1. `SpellFire.MemoryRobot` 被 `SpellFire.RuntimeHost`、`SpellFire.WowRuntime` 消费
2. `SpellFire.RuntimeHost` 被 `SpellFire.WowRuntime`、`SpellFire.Runtime` 消费
3. `SpellFire.WowRuntime` 被 `SpellFire.Runtime` 消费
4. `SpellFire.NavMesh` 被 `SpellFire.Runtime` 消费
5. `SpellFire.Runtime` 被 `Primer` 和测试壳消费

## 禁止事项

1. 禁止把四大件重新塞回 `Well` 里冒充完成
2. 禁止第一刀就追求 Products、授权链、全自动启动
3. 禁止把 `fasmdll_managed.dll` 包装成四大件之一
4. 禁止先写一层新的大反射包装继续长期依赖第三方 DLL 冒充自研
5. 禁止在还没抽出内存底座前，直接大规模写 WoW 语义 API

## 验收方式

本蓝图阶段的验收不是运行截图，而是边界明确：

1. 四大件职责分工明确
2. `Well` 与未来四层的关系明确
3. `fasmdll_managed.dll` 口径明确
4. 第一阶段第一刀明确
5. 后续项目骨架有清晰落点

## 停工条件

出现以下情况，本专项应暂停继续空谈，直接进入第一刀实施：

1. 四层职责已经清楚
2. 第一刀目标已经清楚
3. 再讨论只会回到“先改 Well 还是先改四大件名字”的循环

当前已满足以上条件。

因此本文件落地后，下一步应直接进入：

1. `SpellFire.MemoryRobot` 项目骨架
2. `Well -> MemoryRobot` 可抽取资产清单
